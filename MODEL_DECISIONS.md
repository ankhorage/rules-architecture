# Built-in architecture models

These are model definitions, not classifications of current Ankhorage repositories. Source paths and folder names are not role assignments. Detection must infer roles from graph relationships and report uncertainty; evaluation needs an explicitly selected target.

- **Hexagonal:** [Cockburn's original Ports and Adapters article](https://alistair.cockburn.us/hexagonal-architecture) describes an application communicating through purposeful ports with replaceable outside adapters. The model treats the core and its ports as the inside boundary. An adapter may depend on a port; the core may not depend on a concrete adapter. A port may refer to core types. The diagram's six sides do not imply six roles or ports.
- **Clean:** [Martin's Clean Architecture article](https://blog.cleancoder.com/uncle-bob/2012/08/13/the-clean-architecture.html) defines the dependency rule as source dependencies pointing inward. The initial model encodes entities, use cases, interface adapters, and frameworks as progressively outer rings; composition is outermost. Control flow can move outward through polymorphism while source dependencies still point inward.
- **Onion:** [Palermo's Onion Architecture article](https://jeffreypalermo.com/2008/07/the-onion-architecture-part-1/) puts the domain core inside and infrastructure outside, with an external implementation depending on a core-owned interface. Presentation and infrastructure are separate outside concerns, so the initial model does not permit either to import the other as an architectural dependency.
- **Layered:** [Fowler's Presentation Domain Data Layering article](https://martinfowler.com/bliki/PresentationDomainDataLayering.html) describes presentation, domain, and data-source layers with dependencies generally running downward. The initial model chooses a strict adjacent-layer variant: presentation depends on domain, domain depends on data source. This differs from the inward-dependency models. A later explicit profile may relax layer skipping without changing the built-in baseline silently.

The allowed-dependency pairs express model semantics after roles are known. They do not establish roles from source directories, assert that a project follows a model, set a target architecture, or assign rule severity.
